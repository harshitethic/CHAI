# Implemented architecture — 0.2.0-alpha.1

Normal ChatGPT is the reasoning provider. The user's first-party login stays in persist:chai-chatgpt; CHAI never reads session credentials. Each logical role has a restricted Chromium view and a saved conversation URL. The main process checks visible 6 High/composer/send controls and delivers only a job ID and role through the normal input UI.

The Broker persists jobs in SQLite. ChatGPT's installed CHAI plugin fetches job instructions, scoped evidence and a JSON schema using chai_get_job, then returns its result with chai_submit_result. No assistant-output scraping or private model endpoints are involved. Role outputs are validated before they enter the Coordinator. Duplicate accepted answers are idempotent; conflicting answers and canceled jobs are rejected. A cached result survives database restart. Sent-job receipts avoid automatic replay of already delivered prompts.

The Coordinator owns Manager assignment → Builder proposal → local approval → execution → independent Reviewer decision → Manager report. Reviews evaluate the original goal. Missing work triggers a new round, never automatic approval. Limits are three rounds, fifteen role attempts and thirty-six actions. Each completed role output and tool effect has a persistent identity.

The Engine controls permissions and effects, not the browser or MCP server. Every plan has an exact-content, fifteen-minute local approval. Python descriptor-relative file operations reject escapes and sensitive paths, snapshot previous content and compare expected content before writes. Commands use a fixed argv allowlist and cancellable process groups. Fresh file content and hashes are supplied for verification. Ambiguous interrupted commands are not replayed.

MCP runs on loopback port 40671 and is exposed by a CHAI-owned quick tunnel or the user's HTTPS forwarding origin. Official MCP SDK routes implement metadata, registration, authorization, token exchange and MCP transport. Registration is limited to ChatGPT HTTPS callbacks. Pairing requires a local native approval and PKCE. PC-tool access/refresh tokens are generated by CHAI; only hashes are stored. Dynamic client metadata is private and may include a client secret. This authorization does not provide model inference access. Disconnect revokes CHAI grants; ordinary shutdown preserves pairing for the same origin.

The renderer has no Node access. Remote provider/browser content has no privileged preload or CHAI IPC. Narrow validated IPC checks the exact packaged renderer URL. Navigation, downloads and device permissions are restricted. Provider popups are restricted to permitted authentication origins and the active CHAI tool origin.

Current manual host tools include isolated browser navigation/click/capture and X11 click/screenshot, each requiring confirmation. They are not yet available as general model-driven actions. Arbitrary terminal execution, broader file management, a persistent hosted endpoint, autostart and whole-PC reboot validation remain backlog items.
